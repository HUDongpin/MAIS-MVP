# Claude Suggestions — MAIS-MVP Development Prompts

**Date:** 2026-08-18

**How this was produced.** A nine-agent audit of this repository: eight parallel analysts (product completeness, architecture & code health, testing & QA, security & auth, curriculum content & data quality, performance & scalability, release process & developer experience, accessibility/i18n/UX) each read the actual code, followed by a critic agent that spot-checked the most severe claims against the source and hunted for whole areas the analysts missed. The result was 55 verified gaps plus 7 missed areas. Every finding below is backed by files and line numbers the auditors read on 2026-08-18 — line numbers will drift as the code changes, but the file paths and function names should stay findable.

**How to use this document.**

- Each prompt is self-contained and ready to paste into a fresh Claude Code session. Follow the session contract: **one prompt = one session = one worktree = one branch** (per `CLAUDE.md`).
- Every prompt states acceptance criteria. Hold the session to them — do not accept "done" without the named tests passing.
- Phases are ordered by risk: Phase 0 closes exposures that are dangerous **today**; later phases build on earlier ones. Within a phase, order matters less.
- A few prompts deliberately overlap (noted inline). When two overlap, give both texts to the *same* session so it reconciles them, rather than running them separately.

## State of the project — the audit's short version

The product is far more real than its README admits: working student, teacher, and parent consoles; ~23,750 questions across seven curriculum tracks in three markets; 270 hand-built interactive CCSS lessons; a RAG-backed AI tutor; and an unusually deep bilingual foundation. The 62 gaps below cluster into five structural weaknesses:

1. **The front door is open.** Anyone on the internet can self-register a teacher account; hardcoded `12345` demo logins authenticate in production with no environment gate; sessions can never be revoked (password reset does not lock out an attacker for up to 7 days); auth rate limits are per-serverless-instance and effectively fictional at load. → *Phase 0*
2. **The product cannot lawfully onboard a real child.** No privacy policy, no terms, no parental consent, no account deletion, no data export, no email verification — and no backups, no error monitoring, and an untested IP posture on textbook-derived content. Every audit missed most of this; the critic caught it. → *Phase 1*
3. **The database is one 74MB JSON row.** Every non-fast-path write re-serializes the entire platform state and re-syncs 22 projection tables under a global lock. One classroom of concurrent students collapses it, and it gets slower every week it is used. The fix pattern is already proven in-repo (PR #94's row-table fast path). → *Phase 2*
4. **The feedback loops lie.** The documented production release path fails on its own gates (dead canonical-root path, 34-worktree strict gate); 213 test files are excluded from CI; the e2e harness has verified false-green modes; ~89% of the 187 API routes have no authorization test. In a repo developed by many concurrent AI sessions, untrustworthy gates mean everything else ships unverified. → *Phase 3*
5. **Content quality is thinner than the numbers suggest.** ~6,000 live mainland/FL questions have their "pending manual QA" status silently rewritten to "approved" at import; the English rendering of all HJB/BNU content is a per-character machine gloss; the HK home market has ~48 primary practice questions total; zero question diagrams shipped against a May audit that flagged ~1,400 questions needing one. → *Phase 5*

Phases 4 (product completeness), 6 (architecture & UX polish), and 7 (strategy) round out the path to a sellable product.

## The five moves that matter most

If you only run a handful of these prompts, run these (the critic's verdict, in order):

1. **Close the front door in one strike** — teacher-registration invite gate + environment-gate the `12345` fast-login accounts. A day or two of work that closes the two worst production exposures. *(Prompts 1–2)*
2. **Child-data legal baseline** — privacy/terms pages, parental consent, account deletion, data export. This gates revenue exactly like a feature gap: no school procurement passes without it. *(Prompt 8)*
3. **Persistence re-architecture on the proven pattern** — pull the ~24MB of immutable curriculum data out of the mutable blob, then extend PR #94's row-store fast path to the top write paths, with a 30-concurrent-user smoke as the gate. *(Prompts 14–16)*
4. **Automated backup with a rehearsed restore, immediately** — because move 3 takes weeks, and until it lands the entire platform is one corruptible Postgres row. *(Prompt 11)*
5. **Make the feedback loops trustworthy** — fix the broken release path, re-enable the 213-file visualization test corpus, add a student-journey e2e smoke to CI. *(Prompts 20, 25, 28)*

### 2. Hardcoded demo/fast-login accounts with password "12345" are reachable in production with no environment gate

**Severity: critical.** Anyone on the internet who reads default accounts.md, the marketing site, or simply guesses can authenticate to a production deployment as a teacher, parent, or student with password "12345". Authenticated demo sessions consume real AI-tutor provider spend (per-user quotas mean each seed account gets its own quota), and a demo teacher session is a foothold for probing teacher APIs. The env knob owners would reach for to change the password is dead documentation, which is worse than absent — it creates false confidence.

```text
In the MAIS-MVP repo, harden the demo-account machinery so hardcoded credentials cannot authenticate on production deployments. Specifically: (1) In lib/server/internalCaliforniaFastLogin.ts, gate `authenticateInternalCaliforniaFastLogin` (and the `getInternalFastNoClassTeacher*` helpers consumed by app/teacher/getTeacherFoundation.ts) behind an explicit opt-in env flag, e.g. `HK_MATH_ENABLE_INTERNAL_FAST_LOGIN === "true"`, defaulting OFF; app/api/auth/login/route.ts line 84 must skip the fast path entirely when the flag is unset. (2) In lib/server/userStore.ts, make `getDemoPassword()` (line ~2160) honor the `HK_MATH_DEMO_PASSWORD` env var that .env.local.example line 110 already documents, falling back to the displayed "12345" only when the demo flag is explicitly enabled; also flip `shouldSeedDemoUser()` (line ~2156) to default OFF on Vercel production (`process.env.VERCEL_ENV === "production"`) unless `HK_MATH_ENABLE_DEMO_USER === "true"`. (3) Update .env.local.example comments and RELEASE.md to describe the new opt-in semantics. Acceptance criteria: with no demo env vars set and NODE_ENV=production, POST /api/auth/login with {"username":"Teacher Scott","password":"12345"} returns 401 and no session cookie; existing tests in lib/server/internalCaliforniaFastLogin.test.ts, lib/server/userStoreDemoLogin.test.ts, and lib/server/userStoreDemoFastPath.test.ts are updated to set the opt-in flags explicitly and still pass; `npm test` (or the repo's node test runner invocation) passes; e2e demo logins keep working because playwright.config.ts webServer env sets the opt-in flags. Do not weaken the flexible-example-account flow for local dev — only gate it by environment.
```

### 3. Sessions cannot be revoked: stateless 7-day HMAC tokens survive logout, password change, and password reset

**Severity: high.** This is a platform holding minors' data. If a child's session cookie leaks (shared school computer, XSS, shoulder-surfed devtools), the account owner has no remedy: changing or resetting the password does NOT lock out the attacker for up to 7 days. This also undermines the password-reset flow's security value entirely, and parent/teacher/admin sessions carry the same exposure with higher blast radius.

```text
In the MAIS-MVP repo, add session revocation on credential change. Approach: add a per-user `session_version` (or `auth_epoch`) integer to the user record in lib/server/userStore.ts (users table schema around line 3069 and the Database type, plus the Postgres hot-auth mirror in `backfillPostgresHotAuthTablesForAdmin` / `getAuthenticatedUserByIdFromHotTables` around line 7500). Embed the version in the session payload in lib/session.ts (extend SessionPayload with `ver`; keep backward compat by treating a missing `ver` as 0 during a migration window, then reject). In lib/server/auth.ts `getAuthenticatedUserFromToken`, reject tokens whose `ver` doesn't match the stored user's current version. Increment the version in `changeAuthenticatedUserPassword` and `resetUserPassword` (lib/server/userStore.ts / lib/server/userStore/authSessionPersistence.ts) so every password change/reset invalidates all outstanding sessions, and have those routes issue a fresh cookie for the requester (app/api/auth/password-change/route.ts already has the request context to call setSessionCookie from lib/server/sessionCookie.ts). Acceptance criteria: a node test proves a token minted before resetUserPassword fails verification afterward while a token minted after succeeds; existing tests in lib/server/userStoreAuthSessionPersistence.test.ts and lib/server/authPasswordAsync.test.ts still pass; login/register flows still set working cookies; middleware.ts continues to work unchanged (it only checks signature/expiry for page redirects — the API-level user lookup is where revocation is enforced, note this in a comment).
```

### 4. Auth brute-force rate limits are in-memory per serverless instance, guarding a 5-character password minimum

**Severity: high.** Children pick passwords like "12345" (the platform's own demo password normalizes exactly that). A distributed credential-stuffing or per-identifier brute-force run against /api/auth/login sidesteps the per-instance counters, and 5-character passwords fall quickly. The same weakness dilutes the parent-child invite-code guessing guard, which protects access to a minor's learning data.

> **Note:** Pairs with the generic durable rate limiter in Phase 2 (prompt 18). Run this one first; the Phase 2 prompt can then reuse the durable store this one introduces. If one session takes both, hand it both texts.

```text
In the MAIS-MVP repo, make auth throttling durable and strengthen the password policy. (1) Add a Postgres-backed (or existing-store-backed) rate limiter for the auth scopes in lib/server/authRouteGuards.ts, following the pattern already proven in lib/server/userStore/aiGovernancePersistence.ts `consumeAiCapabilityRateLimit` (line 1934) which persists admitted-request events and evaluates windows against the database; fall back to the in-memory limiter only when durable storage is unavailable, and keep the in-memory limiter for local dev. Wire it into app/api/auth/login/route.ts, app/api/auth/password-reset/request/route.ts, app/api/auth/password-reset/confirm/route.ts, app/api/auth/password-change/route.ts, and app/api/parent/children/link/route.ts. Also stop trusting `x-real-ip` in clientIpForRequest (authRouteGuards.ts line 69-75) — on Vercel use the platform-set x-forwarded-for first hop only. (2) Raise the minimum password length from 5 to 8 for teacher/parent/admin roles and 6 for students in app/api/auth/register/route.ts (lines 86, 128), app/api/auth/password-reset/confirm/route.ts (line 34), lib/server/userStore.ts line ~7437, and the bootstrap-admin check in lib/server/userStore/authSessionPersistence.ts line 1046, rejecting the exact strings "12345"/"123456"/"password". Update client-side validation and copy where the UI states the 5-character rule (grep for "at least 5"). Acceptance criteria: node tests prove a 13th login attempt for one identifier within 15 minutes is 429 across two simulated "instances" (two limiter instances sharing the durable store); registration with a 5-char teacher password returns 400; lib/server/authRouteGuards.test.ts and userStoreAuth tests updated and passing; the HK_MATH_E2E_LOGIN_IDENTIFIER_MAX e2e escape hatch (authRouteGuards.ts line 43) keeps working.
```

### 5. Password-reset flow has a production token-exposure switch and an account-existence oracle

**Severity: medium.** The env flag is a standing footgun: it exists precisely so someone can flip it on a deployed environment ("expose local reset links"), and if it is ever set on production — or on a preview deployment sharing the production Postgres — any account including admin can be taken over with a single unauthenticated POST. The delivery-status oracle lets an attacker enumerate which emails/usernames belong to real accounts (students' parents included) for targeted phishing.

```text
In the MAIS-MVP repo, harden the password-reset request flow in app/api/auth/password-reset/request/route.ts and lib/server/passwordResetRequest.ts. (1) Remove the HK_MATH_EXPOSE_LOCAL_RESET_LINKS production override: change the exposeLocalResetLinks computation (route.ts lines 16-17) so reset URLs can only be returned when NODE_ENV !== "production" AND the deployment is not Vercel production (`process.env.VERCEL_ENV !== "production"`) — delete the env-var escape hatch entirely, or if the owner needs it for staging demos, require it to be paired with a non-production VERCEL_ENV. (2) Close the enumeration oracle in passwordResetRequest.ts lines 83-104: make the response body identical whether or not the account exists — always return only {ok: true, message}, moving delivery status/channel into a server-side log (the existing warn() dependency) instead of the response; keep resetUrl/expiresAt only under the (now stricter) local-dev branch. Update lib/server/passwordResetRequest.test.ts accordingly, including a test asserting byte-identical response bodies for existing vs non-existing identifiers in production mode, and a test asserting no resetUrl in any production-mode response regardless of env vars. Acceptance criteria: all passwordReset* tests pass; the local-dev DX (reset link shown in dev without email delivery configured) still works with NODE_ENV=development; grep confirms HK_MATH_EXPOSE_LOCAL_RESET_LINKS is gone from code or provably inert in production, and RELEASE.md's env inventory is updated.
```

### 6. No security headers: zero CSP, X-Frame-Options, HSTS, Referrer-Policy, or Permissions-Policy anywhere

**Severity: medium.** The app renders LLM-generated tutor output, RAG evidence text, forum content, and teacher-authored material to logged-in children — any single XSS becomes durable session-cookie-adjacent compromise (the cookie is httpOnly, but XSS can still drive authenticated API calls including AI-tutor spend and PII reads). Without frame-ancestors the login page can be clickjacked; without HSTS first-visit downgrade attacks are possible; without Referrer-Policy, URLs (which include password-reset tokens per the /reset-password?token=... pattern in lib/server/passwordResetDelivery.ts line 108) can leak via referrer to any external resource a page loads.

> **Note:** The critic verified this claim is very slightly overstated: vercel.json does set `X-Content-Type-Options: nosniff`. Everything else — CSP, HSTS, X-Frame-Options, Referrer-Policy, Permissions-Policy — is genuinely absent.

```text
In the MAIS-MVP repo, add a security-header baseline. In next.config.ts add an async headers() function applying to "/(.*)": Strict-Transport-Security "max-age=31536000; includeSubDomains", X-Frame-Options "DENY", Referrer-Policy "strict-origin-when-cross-origin", Permissions-Policy disabling camera/geolocation/payment (keep microphone available if the AI-tutor speech input at app/api/ai-tutor/speech needs it — check components using getUserMedia first), and a Content-Security-Policy. Build the CSP by auditing actual usage: the app uses Next.js App Router with React 19, Framer Motion, three.js (transpilePackages in next.config.ts), inline styles from Tailwind — start with default-src 'self'; script-src 'self' 'unsafe-inline' (Next requires it without nonces; if feasible, implement nonce-based CSP via middleware.ts instead); img-src 'self' data: blob:; media-src 'self' blob:; connect-src 'self' plus the websocket origins the realtime tutor uses client-side if any (grep for wss:// in client components); frame-ancestors 'none'. Verify no external font/CDN dependencies exist before locking font-src/style-src. Also change the password-reset URL flow to carry the token outside the query string OR add Referrer-Policy no-referrer specifically on the /reset-password page. Acceptance criteria: `npm run build` succeeds; a Playwright smoke test asserts the headers are present on / and /login responses; the AI tutor chat, speech input, lesson three.js visualizations, and login flow all still function in the e2e suite (these are the pages most likely to break under CSP); document the chosen policy in RELEASE.md.
```

### 7. Master secrets live as plaintext files in the working tree of a multi-agent repo, protected only by .gitignore and release-script exclusions

### 11. Backup and disaster recovery for the single-row production database
