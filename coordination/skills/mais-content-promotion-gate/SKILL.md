# MAIS Content Promotion Gate

Treat the repository's native Manifest, Receipt, Closure, Registry, checker ledger, and CI artifacts as authoritative. This skill produces only redacted audit and handoff summaries; never present a skill-generated summary as a native Receipt.

Default to an offline, read-only audit. Do not stage, commit, push, deploy, call a provider, access credentials, or write live surfaces. A user request to inspect a gate does not authorize Shadow execution, baseline re-affirmation, integration, or release.

## Route the request

1. **Discover or audit:** run `node scripts/discover-promotion-gate.mjs --repo <repo> [--expected-head <sha>]`. Read [discovery-and-routing.md](references/discovery-and-routing.md).
2. **Validate, Shadow, or verify:** first perform operation-aware discovery. Use `run-native-gate.mjs` only with explicit `--execute`. Both `shadow` and `verify-receipt` are Shadow-capable because the native verifier replays the registered execution; require `--allow-shadow` (or the verify-only alias `--allow-replay-shadow`) before even planning/discovery. Dry-run output must retain `wouldExecute=false`. Validate and Shadow run only from the registered execution commit, where a future canonical Receipt must not exist. Verification additionally requires the later finalization/storage commit, repository-relative Receipt path, and authorized file SHA-256; the wrapper reads the exact Git blob and copies only those verified bytes to its private temporary input. It invokes only the exact repository-advertised operation, emits a redacted digest summary, and blocks unresolved re-affirmation. Read [core-contract.md](references/core-contract.md).
3. **Compare canonical/fresh/replay Receipts:** run `compare-receipts.mjs --repo <repo> --manifest <workflow-selected-repo-path> --canonical <file> --fresh <file> --replay <file>`. The public CLI never accepts a caller-selected schema; it discovers the closed schema through the tracked/current Manifest, raw-bound ledger entry, immutable checker release bundle, Git blob/mode, current HEAD, and release ancestry. Equal raw digests are not required. The comparator recomputes each declared raw and semantic digest, enforces the generic non-live governance envelope, and requires exact duplicated bindings plus three distinct run identities. Candidate-specific semantic proofs remain owned by the native schema and checker, never by this skill. Read [lifecycle-and-invalidation.md](references/lifecycle-and-invalidation.md).
4. **Finalize Shadow:** require the native finalizer and exact A11/A22/GitHub/A25 external evidence. A validation pass alone leaves the Manifest at `shadow_ready`; only Receipt plus Closure/Registry evidence can establish `shadow_passed`.
5. **Prepare live work:** stop at a redacted handoff. Read [release-handoff.md](references/release-handoff.md), then hand deployment, same-SHA live readback, and production rollback to `mais-release-hygiene-deploy-workflow`.

Read [evidence-boundaries.md](references/evidence-boundaries.md) whenever reporting maturity or proof. Read [mais-v2-attempts-case-study.md](references/mais-v2-attempts-case-study.md) only for a named dated v2 attempt, re-affirmation snapshot, or failure-corpus request; it is not a generic contract.

Before answering any of the five core Promotion scenario families, read [response-cards.md](references/response-cards.md), select exactly one primary card, and use every applicable line as the outward-response checklist. A prompt that names a dated attempt, re-affirmation snapshot, cached maturity statement, or role-evidence count also requires the dated case study; preserve its recorded facts as dated evidence instead of converting them to unknown.

## Required response projection

After discovery or validation, report the repository-derived fields explicitly; do not compress them into “exact binding,” “current evidence,” or similar prose:

- identify the workflow-selected active Manifest and canonical Receipt by redacted reference plus hash, and keep any direct base Manifest/Receipt/Closure/Registry in a separate historical evidence layer;
- report the complete relation projection individually: `attemptRelation.relation`, `attemptRelation.baseAttemptRef`, `attemptRelation.revisionRef`, `attemptRelation.baseCount`, `attemptRelation.candidateChanged`, `attemptRelation.sourceChanged`, `attemptRelation.checkerChanged`, `attemptRelation.baselineChanged`, `attemptRelation.reviewedBaselineOnly`, `attemptRelation.directParentManifestSha256`, `attemptRelation.directParentReceiptSha256`, `attemptRelation.evidenceCommit`, `attemptRelation.bindingCommit`, `attemptRelation.executionCommit`, `attemptRelation.storageCommit`, `attemptRelation.finalizationCommit`, and `attemptRelation.historicalClosureOverwritten`, together with status, currentness, lifecycle state, live boundary, and `liveAllowed=false`;
- keep four evidence layers separate: canonical Receipt digest/check verification, repository-native validate authority, canonical/fresh/replay comparison, and Closure/Registry finalization. A pass in one layer never fills another;
- report role-file quantity as a count of bound evidence records. Do not call them independent reviewers unless separate identity/independence evidence proves that claim;
- for Receipt comparison, state that each Receipt first passed the discovered closed checker schema and generic non-live governance grammar, then emit only recomputed comparison/raw/semantic hashes and fixed issue codes. Never emit raw paths or run IDs;
- before giving a mutation disposition, explicitly choose among candidate bytes/semantics change, evidence-only correction, and independently reviewed baseline-only re-affirmation, and state why the other routes do not apply;
- when live work is requested, instantiate every field in `assets/live-release-handoff.template.md` or mark the missing field as a blocker. Name the live-surface owner and A11/A22/A25 same-SHA evidence separately, and route dirty-tree slicing, build, Vercel deployment, same-SHA readback, production rollback, and monitoring to `mais-release-hygiene-deploy-workflow`.

A Shadow-to-live refusal is incomplete unless its handoff inventory names `bindings.candidateDigest`, `bindings.sourceCommit`, `bindings.targetBaselineCommit`, `bindings.checkerVersionSha256`, `bindings.checkerBundleDigest`, `bindings.checkerReleaseCommit`, `lifecycleState`, `currentness`, `liveBoundary`, the complete `attemptRelation` projection above, and the complete comparison projection: `receiptComparison.canonical`, `receiptComparison.fresh`, `receiptComparison.replay`, `receiptComparison.bindingsEqual`, `receiptComparison.semanticDigestsEqual`, `receiptComparison.rawDigestsEqual`, `receiptComparison.runIdsDistinct`, `receiptComparison.semanticDigestsVerified`, and `receiptComparison.comparisonStatus`. When comparison status is `pass`, also require `receiptComparison.comparisonDigest`. Do not replace either projection with a generic “exact bindings” phrase, even when deployment is already blocked for another reason.

Missing facts remain `unknown`, `not-run`, or blocked. Do not turn an omitted field into a favorable inference.

## Non-negotiable decisions

- Preserve the common `EvidenceEnvelopeV1` fields and the Promotion extension in `assets/promotion-gate-handoff.schema.json`.
- Keep `lifecycleState`, `currentness`, and `liveBoundary` separate. Re-affirmation is a revision relation, not a lifecycle state.
- Candidate bytes, candidate semantics, or checker contract changes require a new immutable attempt. Never update a frozen hash or Receipt in place.
- Permit append-only baseline re-affirmation only after independent evidence shows the reviewed baseline delta is unrelated to candidate semantics. Use three immutable phases: baseline-only A11/A22/A25 evidence first; one preparation/binding commit containing the revision Manifest and descriptor as the registered execution SHA; then a later Receipt/finalization commit. The descriptor binds the base Manifest/Receipt/Closure/Registry, revision Manifest, unchanged candidate/source/checker facts, changed-path digest, and evidence commit, but never pre-binds its own commit or a future revision Receipt hash.
- Protected runtime drift makes a prior Receipt `historical-only` until the repository-native currentness validator passes a properly re-affirmed revision.
- Candidate, protected-path, HEAD, or worktree mutation during execution invalidates the run.
- Require exactly the public `promotion:validate`, `promotion:shadow`, and `promotion:verify-receipt` scripts. Reject extra `promotion:*` commands and require validate -> validate, Shadow -> Shadow, and verify -> verify; never let build logic remap them.
- Count workflow obligations only from reachable executable YAML `run` commands in one supported Linux job using bash/sh. Structurally inspect job/step `if` and `shell`; fail on disabled or ambiguous evidence steps. Comments, echo/printf strings, heredoc bodies, quoted dead text, constant-false branches, and commands after unconditional `exit`/`return` are not workflow proof. Reachable shell functions may carry proof.
- Once a workflow contains Promotion evidence, parse its top-level, selected-job, and step authority/control mappings with closed key sets. Reject duplicate or unknown fields and reject weakening controls such as `continue-on-error` or unsupported timeouts; unrelated workflows with no Promotion evidence are outside this parser's authority boundary. Within the selected Promotion job, reject every reachable plain `JSON.parse` except the single occurrence inside the exact already-proven native semantic comparator program. Any other parser, altered comparator, or injected occurrence makes discovery audit-only and fail-closed.
- Require validate, fresh Shadow, and a provably distinct replay in that order. After both Shadows finish, allow the exact three Receipt verifications and the semantic comparison in either order, but require all four operations to be reachable, unconditional, and complete before job success. Expand helper call sites and require exactly one fresh, replay, and canonical verification; reject missing, duplicate, dynamic, or unreachable helper targets. Dynamic fresh/replay IDs are distinct only when they use the same expressions and a guaranteed non-empty literal prefix or suffix difference.
- Accept semantic comparison authority in exactly two forms: a strict tracked/current inline `node --input-type=module -e` program whose three arguments and complete fail-on-mismatch semantics are proven, or an exact repository-relative external comparator entry that is bound into the checker release bundle. For the inline form, bind authority to the workflow bytes/SHA-256/Git blob/mode and exact program SHA-256; do not claim that the inline program belongs to the checker release. Reject no-op, injected, weakened, or extra comparator programs.
- For an inline comparator, accept only plain literal throw messages or the exact proven digest-list interpolation used by the tracked program. Reject executable/interpolated throw payloads, command substitution, wrapper indirection (`npx`, `npm exec`, `pnpm dlx`, `yarn dlx`, `bunx`), network/remote tools, and direct deploy/cloud/database/provider CLIs. Account for the selected job exactly: one validate, two Shadow invocations, three unique Receipt verifications, and one proven comparator; any additional relevant invocation fails closed.
- Treat every package, workflow, selector, ledger, bundle file, schema, Manifest, Receipt, Closure, Registry, re-affirmation descriptor, and invoked CLI as authoritative input: it must be repository-contained, have no symlink component, and match the current HEAD blob bytes and executable mode. Ignored or untracked local artifacts are not current evidence.
- Parse every package-owned authoritative JSON input with one bounded recursive strict parser before semantic validation. Buffer decoding uses fatal UTF-8, numbers must remain finite, and byte/depth/work limits apply before or during parsing. Reject duplicate keys at every depth without echoing their names or values; ordinary `JSON.parse` is not authority for current files, commit-tree blobs, schemas, native output, or Receipt comparison inputs.
- Resolve checker/source commits and ancestry, recompute the ledger raw SHA-256 and documented checker bundle digest, parse bundled schemas, and bind checker release commit in every comparison.
- Bind comparison authority to the workflow-selected Manifest and tracked canonical Receipt, including their raw SHA-256, Git blob/mode, and canonical execution commit. The public CLI must read the supplied canonical bytes, require their identity to equal that tracked artifact, and require canonical/fresh/replay binding projections to equal the trusted Manifest/canonical execution projection. A caller cannot substitute a schema or a consistently rehashed but wrong candidate binding.
- Classify native output by the fields the authoritative CLI actually emits. A validate PASS proves only the selected current Manifest validation fields; a verify PASS proves only the named Receipt's digest verification fields. Do not fill omitted facts from discovery or promote either result to current Shadow or `shadow_passed` authority. A Shadow Receipt and canonical/fresh/replay comparison still require the complete candidate/source/baseline/checker-release/execution/direct-Manifest binding.
- An active nested re-affirmation without a workflow-selected machine descriptor may still be discovered mechanically. Resolve the nearest ancestor that has one complete Manifest/Receipt pair, skipping incomplete intermediate records; mark the selection `unresolved-reaffirmation`, `blocked`, and `stale`. Retain the original attempt's verified Closure/Registry only as `historical-direct-base`, and do not authorize native execution or infer authority from directory names.
- Validate every Receipt against the exact closed checker-release schema; never select a reduced fixture or caller-version grammar. On top of that native schema, enforce only the version-independent Promotion governance envelope: exact candidate/source/baseline/checker/Manifest/execution cross-bindings, generic provenance/worktree/currentness evidence, zero network/provider/database/deploy/production/Registry/live side effects, and temporary-output-only rollback. Candidate-domain proof fields and meanings remain repository-native. Reject production/deploy/approval claims even when all three Receipts have been consistently rehashed.
- Treat the `external-side-effects` proof as a structurally exact, version-independent safe role family: the base ID or a positive numeric `-vN` suffix is allowed only with the expected zero-count/digest proof shape. Reject arbitrary role suffixes and never encode one exact version as normative authority.
- Shadow rollback proves only owned temporary-output isolation. It does not prove database, content, deployment, or live rollback.
- `liveAllowed=false`, a green required check, and `Shadow-mature / live-unproven` must remain explicit until separate same-SHA live evidence exists.
- N role evidence files are N bound evidence records, not proof of N independent reviewers.
- If selectors are multiple/ambiguous, checker release is unresolved, expected HEAD differs, native output is malformed, or bindings disagree, fail closed.
- Closure/Registry filenames or existence are not proof. Validate their schemas, self-digests/event chain, exact direct parents, non-live transition, canonical/replay signatures, A11 replay, A22 clean isolation, repository-recorded GitHub PR/required/main evidence, and A25 closeout. Repository-recorded GitHub evidence is still not fresh provider/API readback.
- Strip `NODE_OPTIONS` and every credential-like environment variable from native child execution. Bound it to 60 seconds and treat timeout/termination as internal error.
- For verification, accept only an explicitly authorized finalization transport: a canonical repo-relative Receipt path, a distinct descendant storage commit, and exact file SHA-256. Read the regular-file Git blob and mode from that commit, verify its SHA-256 before discovery, and copy only those verified bytes into a private wrapper-owned temporary file for the native verifier. The current checkout must remain the registered execution commit; reject absolute, traversal, symlink, external, untracked, mismatched, same-commit, or non-descendant inputs.
- A base-attempt validate or Shadow operation must prove through the repository tree that the future canonical Receipt is absent at the registered execution commit; otherwise stop with `FUTURE_CANONICAL_RECEIPT_ALREADY_BOUND` before native execution. Audit may still describe an already-finalized Receipt without authorizing a new base execution.
- Never infer historical storage or finalization identity from the audit-time HEAD. Populate them only from explicit verified Receipt transport/finalizer evidence. A non-null release handoff requires the async repository-backed builder/validator to cross-bind canonical Receipt evidence and prove execution -> storage -> finalization -> intended release ancestry; caller-supplied ancestry booleans are not authority.
- Treat `x-resolver-enforced=promotion-gate-handoff-v1` as an executable cross-field contract: the public async validator always uses this package's fixed bundled schema, requires an exact non-public canonical Receipt transport, independently reads actual repository `HEAD`, and requires every duplicated release binding/artifact plus both release SHA fields to match it. It re-proves the exact regular Git blob bytes/mode/object at storage, absence at execution, and execution -> storage -> finalization -> actual-release ancestry. It also independently resolves the unique Promotion workflow, selected Manifest, raw-bound ledger, immutable checker bundle, and unique closed Receipt schema; the stored bytes must validate as a passing native Receipt with recomputed self-digests, semantic digest, raw digest, and canonical binding projection. Caller schemas, summaries, pass flags, and precomputed authority hashes are never accepted. Storage may equal finalization only when both identify that same verified transport commit; execution remains distinct. Unsupported JSON Schema assertion keywords fail closed; `not` is enforced.

Use the templates in `assets/` for human-readable outputs. Include only hashes and redacted references; omit raw candidate content, opaque external identifiers, credentials, provider output, and unbounded file paths.
