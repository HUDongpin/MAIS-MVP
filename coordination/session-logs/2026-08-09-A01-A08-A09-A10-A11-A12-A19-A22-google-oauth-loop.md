Implemented behavior:

- OAuth 2.0 authorization-code/OpenID Connect flow with PKCE S256, encrypted state, nonce, a ten-minute pending cookie, canonical base64url parsing, exact callback validation, and bounded provider/JWKS requests.
- Server-side RS256 ID-token verification for signature, issuer, audience, authorized party, nonce, subject, verified email, expiry, and future-issued-time bounds.

- Host-only sessions are never moved between aliases. An alias-host link attempt is sent to the canonical login page and must reauthenticate there.
- New Student Google login requires a dedicated same-origin `application/x-www-form-urlencoded` confirmation POST with an exact supported publisher and grade. Direct GET, cross-origin POST, absent confirmation, hidden curricula, and non-US Kindergarten combinations fail before OAuth state creation.

## Residual nonblocking security notes

- OAuth state is encrypted, cookie-bound, short-lived, and cleared on the response, but its transaction ID is not atomically consumed in a durable server store. Concurrent replay before the response clear could reach the callback verification twice; Google's authorization code is one-time, and identity persistence is idempotent/conflict-safe. A future high-assurance hardening package can add a transactional consumed-state/JTI store.
- Local password registration currently does not verify ownership of the submitted email. The OAuth implementation therefore refuses every automatic email-collision link, preventing account takeover, but an attacker can still pre-register another person's email and create availability/support friction. Email verification/recovery should be a separate auth-platform package.
